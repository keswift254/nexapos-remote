# NexaPOS 1.0.96

**A shop that was offline for a long time syncs completely when it is back online - also across app updates.** The owner asked, after the Windows 7 PC caught up once it was online again, that shops offline for a while still sync, all at once, when they get online, and that future updates do not break this. Testing a whole shop offline for two months (a PC, a till that only reaches the shop over the LAN, the owner's phone online all along, an app update half-way, the server's daily clean-up) found and fixed these:

- **A change to a record another device made never went up.** A price changed on the PC for an item added on a phone, a password changed on a phone, an expense removed on another till: the record kept the other device's name with this device's change number, so the upload (which sends this device's own changes) never sent it, the dashboard never counted it as waiting, and over the LAN it travelled under the other device's name with a number that device may have used for something else - one way "A source revision was already recorded with different content" came about, and the other device then skipped its own real change of that number. Every change is now the changing device's own (a database rule, so every screen, present and future, follows it). Edits made before this update that are still only on the device go up once after updating, with what they say and when they were made kept exactly.
- **A till that only ever reaches the shop over the LAN** (its sales passed on by a PC that is online): one of its changes the server refused (a wrong date on that till, say) made the PC drop every queued change of that till. Now only that one change is dropped; the rest go up.
- **A row whose parent never reached the shop** (a sale line whose sale was refused) stopped the device's download at that page for good - nothing the shop did afterwards arrived. It is now saved anyway, and links up when its parent arrives.
- **A guard for future updates:** an update may add to the database, but never change a shop's existing records (content, time, change number or device) - a test fails the release if one does. Plus a test of the whole two-month-offline shop, run on every release.

**M-Pesa Till/Paybill: a sale paid in two or more payments.** A customer who sent 200, then 50, for a sale of 250: tap each payment (they are listed under "Paid a different amount, or in two or more payments?"). The cart shows what they add up to ("KES 200.00 + KES 50.00 = KES 250.00 of KES 250.00. Paid in full"). On Complete Sale each payment's code is used on the sale for exactly its own amount - the shop refuses a code another sale used - and the sale is saved with every code on its receipt. Payments that do not cover the sale, or one the sale does not need, are refused before anything is used; paid more is asked about (the rest goes back in cash); if any code is refused or the sale cannot be saved, the codes already used are given back. Works with cash first, then two or more till payments for the rest. At most five payments for one sale. NexaPOS Lite (the iPad) does the same (build 2026-11-26.2).

**The cart's search stays at the top.** However many items are in the cart, the search box (now made to stand out) and what it finds stay at the top while the cart scrolls under them. Each result says whether the item is already **In cart** (how many) or **In inventory** (how many in stock). Picking one that is already in the cart takes you to its line - brought into sight, marked for a moment, the cursor on its + (Enter adds one more) - instead of adding it a second time. A barcode scan still adds one more, as before.
